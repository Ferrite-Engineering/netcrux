## 2. Tech Stack

### 2.1 Core Framework

Same baseline as WaveCrux: Flutter (Dart) + Riverpod with code generation. See `wavecrux/docs/ARCHITECTURE.md` §2.1 for the full table and rationale.

### 2.2 Domain Engine

RTL elaboration runs through **`crux_yosys`** (the shared workspace package at `crux-shared/packages/crux_yosys`), which runs Yosys as a subprocess to produce a `write_json` netlist. VHDL sources are first lowered to Verilog by a standalone `ghdl --synth --out=verilog` subprocess and read by Yosys with `read_verilog`; no GHDL Yosys plugin is involved. The document is parsed by the streaming reader in `lib/services/yosys/` (per-module slicing, O(largest module) live) on a background isolate (`parseNetlistOnIsolate`), never on the UI thread. Graph layout is delegated to **elkjs** (the Eclipse Layout Kernel) — vendored at `assets/elk/elk.bundled.js`, run on desktop as the vendored native Rust port `native/vendor/elkrs` through the C ABI of `native/elk_ffi` (`lib/services/layout/native_elk_solver.dart`; elkjs on a `flutter_js` JavaScript engine remains the fallback and the `NETCRUX_LAYOUT_ENGINE=elkjs` escape hatch, chosen by `lib/services/layout/layout_engine_selection.dart`) and natively in the browser on web (see §3), behind `lib/services/layout/elk_layout_service.dart`.

### 2.3 Rendering

Custom canvas rendering, not a plain widget tree. The schematic is painted by `lib/features/viewer/rendering/schematic_painter.dart` (a `CustomPainter`/`RenderBox`-backed canvas) with a **3-band level-of-detail system** — `lib/features/viewer/rendering/lod_band.dart` (`enum LodBand { overview, mid, detail }`, `LodBandRouter.bandFor(zoom)`) — so large netlists degrade gracefully as the viewport zooms out. The painter's viewport cull, the click hit-test and the keyboard walk's reading order all read one per-scope index, `lib/features/viewer/rendering/schematic_scene_index.dart` — a bucket grid over cells, pins, module ports and wire segments, built once per laid-out graph — rather than scanning the whole scope on every frame, click and keypress; it returns candidates in scope order and each caller keeps its exact test, so the answers are the ones the full scan gave. Cell bodies are drawn through the `cellBodyPainterFactoryProvider` seam (a Pro overlay extension point; see §10).

**Camera behaviour on resize.** `ViewportTransform` is `screen = design * zoom + offset`, with `offset` in absolute screen pixels — so a viewport that changes size (window resize, panel-splitter drag) moves the design unless something re-aims the camera. `SchematicGestureHandler` notices the size change during layout (a resize schedules no rebuild, so nothing else would) and calls `ViewportTransformNotifier.handleViewportResize`, which branches on whether the user has touched the camera:

| State | On resize |
|---|---|
| Still the result of a fit — nothing panned or zoomed since | Re-fit to the new viewport: a wider pane shows the same design larger, not the same design plus empty space |
| Panned, zoomed, or revealed to an element | Zoom is left exactly as the user set it, and the design point under the old viewport centre is kept under the new one |

The second row is what every canvas tool does — a resize reveals more or less of the design rather than rescaling what you were looking at — and the first is the fit-to-window behaviour users expect from a view they have not touched. `ViewportTransformNotifier` tracks this with `_fittedBounds`, set by `fitToBounds` and cleared by `pan` / `zoomAt` / `setZoom` / `reset` / `revealBounds`.

### 2.4 Panel Layout

Multi-pane IDE layout ships via **`crux_ide_layout`** (the shared workspace package), wrapped by `lib/features/viewer/widgets/netcrux_ide_layout.dart` (`NetcruxIdeLayout`). `NetcruxIdeLayout` is the only layout on every platform; `package:panes` itself has zero imports anywhere in `netcrux` or the Pro overlay and is pulled in only transitively, by `crux_ide_layout`'s own `pubspec.yaml` (it is not a direct dependency of this repo's `pubspec.yaml`).

### 2.5 Infrastructure

GitHub Actions, under `.github/workflows/`: `ci.yml` (analyze, tests and release builds on push, pull request and a weekly schedule), `integration-desktop.yml` (the macOS integration journeys, weekly), `web-deploy.yml` (manual deploy of the web build to Cloudflare Workers Static Assets, per `wrangler.jsonc`), plus coverage, performance, docs-site and dependency-canary jobs. Signed desktop installers are built by the Pro overlay repository, not here.

## 6. Architecture

### 6.1 Layer Responsibilities

Same pattern as WaveCrux:

- **Domain layer** (`lib/domain/`) — Pure Dart, zero Flutter imports.
- **Services layer** (`lib/services/`) — Business logic.
- **Feature modules** (`lib/features/`) — Each owns its providers, screens, widgets.
- **Core** (`lib/core/`) — Theme, constants, shortcuts, utilities.
- **Shared** (`lib/shared/`) — Leaf UI atoms reused across features (tier badges, …).
- **Plugins** (`lib/plugins/`) — Registry infrastructure (when needed).
- **Composition root** — the files directly under `lib/` (`app.dart`, `main.dart`, `app_router.dart`, `netcrux_color_theme_bootstrap.dart`) wire the layers together and are exempt from the layer matrix; no layer imports them back.

### 6.2 Dependency Flow

Enforced by `test/static/import_layering_test.dart`. The matrix — each layer and what it may import:

```
domain/   → domain only            (hermetic: no Flutter, no Riverpod)
services/ → domain, services, l10n (never features — see allowlist below)
features/ → anything               (lateral widgets/screens: workspace shell only)
core/     → core, l10n             (SDK + localized labels)
shared/   → shared, core, domain, l10n
plugins/  → plugins, domain
```

One deliberate carve-out, encoded as an explicit commented allowlist in the static guard, plus a second allowlist that is empty by design:

- **Composition allowlist (services → features).** A small named ring of wiring modules whose *purpose* is binding feature state across boundaries: the per-tab / per-pane ProviderScope override lists, the session save/restore controller, the CXP inbound/outbound bridge pair, the source-file auto-reload watcher, the Yosys executable provider (reads `appSettingsProvider`), and the workspace notifier (its launch-restore gate reads the `restoreTabsOnLaunch` setting). These import feature providers by design; anything else in `services/` reaching into `features/` fails the guard. When a wiring file stops importing features, a companion test forces the stale allowlist entry to be removed.
- **Lateral feature imports.** A feature may import a sibling feature's `providers/`, `models/`, `selection/`, and `services/` — cross-feature state reads are how Riverpod apps compose. A sibling's `widgets/` and `screens/` are off-limits except from the `workspace` shell (whose job is mounting everyone's panels). The guard's lateral allowlist is empty and a companion test holds it that way. The two entries it once carried both reached `WorkspaceManagersScope` from `features/remote/`; that widget is an inherited holder for the per-tab and per-pane `ProviderContainer` managers — plumbing every layer may depend on, not workspace UI — so it lives at `lib/shared/widgets/workspace_managers_scope.dart` and the imports are ordinary `shared/` reads. A widget two features both need is `shared/` infrastructure; move it rather than blessing the lateral import.

Pure seam types shared across layers live in `domain/models/` — `SelectedElement` / `Selection` / `buildElementPath` (`domain/models/selection/`) and `TraceOverlay` / `TraceOverlayMode` (`domain/models/trace/`) moved there under this ruling; their Riverpod notifiers stay in `features/viewer/providers/`. When a service or interface needs a type currently trapped in a feature, move the type to domain — do not import the feature or add an allowlist entry for a type problem.

### 6.4 Riverpod Provider Hierarchy

`bootstrap()` in `lib/app.dart` builds the root `ProviderContainer` explicitly and adopts it with an `UncontrolledProviderScope`. Open-core overrides are placed first; Pro overrides are spread last from the Pro overlay's override list (`extraOverrides`), so a Pro override wins on conflict.

The hierarchy is two levels deep. Every open tab gets a **child** `ProviderContainer` parented to the root, built by `TabContainerManager` from `netcruxTabOverridesFactory` (`lib/services/workspace/netcrux_tab_overrides.dart`) unioned with the Pro overlay's `proTabOverrides` (passed down as `extraTabOverrides`). Providers holding per-tab state are re-bound in that factory; widgets inside a tab's subtree read them from the tab container. The open-core half of that membership is exactly:

<!-- inventory: netcruxTabOverridesFactory -->
`cdcAnalysisStateProvider`, `cdcSeverityFilterProvider`, `collabPresenceOverlayProvider`, `currentLaidOutGraphProvider`, `currentProjectProvider`, `elaborationDiagnosticFilterProvider`, `elaborationDiagnosticsProvider`, `elaborationStderrProvider`, `filteredElaborationDiagnosticsProvider`, `hierarchyTreeProvider`, `layoutTimingProvider`, `loadedNetlistProvider`, `netlistFootprintProvider`, `perTabCdcAnalysisResultProvider`, `revealRequestProvider`, `schematicCanvasKeyProvider`, `scopeFlashProvider`, `selectedCdcCrossingProvider`, `selectedClockDomainProvider`, `selectedElementProvider`, `sourceFileWatcherProvider`, `sourcePaneStateProvider`, `sourceReloadEventsProvider`, `traceOverlayProvider`, `viewportTransformProvider`
<!-- /inventory -->

That list is not maintained by hand: `test/static/doc_truth_test.dart` compares it against the factory literal and fails on any divergence in either direction. The Pro overlay's per-tab additions (reset-domain, FSM, diff, activity, X-trace, cross-probe) are inventoried the same way in the overlay.

A provider that reads per-tab state but is not itself re-bound per tab is hoisted to the root and silently reads the empty root-scope copy. That failure mode is silent by construction, so it is policed statically by `test/static/per_tab_provider_scope_leak_test.dart` (and its Pro-overlay twin), which computes the taint closure over the provider read-graph — including chains that pass through intermediate providers or cross the open-core/Pro repo boundary.

The scan resolves the tree with `package:analyzer` and works on elements rather than on text, which is what lets it see reads that no textual match can reach. A provider is recognized by its static type inheriting from a riverpod type, so hand-written providers, `@riverpod`-generated providers and families are all registered without depending on the variable's name. A read is recognized by the *receiver's* type being `Ref` or `WidgetRef`, so a read through a `Ref` stored on a field counts; reads are then gathered over the call graph out of the provider's body, so a read hidden in a helper object, an extension method on `Ref`, or a private notifier method is reached and the reported reach names the helper chain it travelled. The provider being read is taken from every element referenced in the argument expression, so a family applied to a run-time argument or a run-time choice between two providers resolves to the underlying symbols — deliberately a may-analysis, since over-approximating costs an allowlist entry while under-approximating restores the blind spot. The shapes the model must resolve are pinned as fixtures under `test/static/scope_leak_shapes/` and asserted by the same test file, so a later simplification of the analysis cannot quietly reopen a closed blind spot.

Resolution costs roughly ten seconds per source root, so the guard stays in the default `flutter test` run rather than behind an opt-in flag: a scope-leak scanner that only CI runs is one that lands broken code all week. `analyzer` is a dev dependency in both repos, pinned below 13.0.0 because analyzer 13+ requires Dart 3.13 and both packages target the 3.12 SDK.

WaveCrux's equivalent per-tab and per-pane architecture is documented in `wavecrux/docs/ARCHITECTURE.md` §6.4. NetCrux mirrors both halves, but its per-pane layer is thin: `PaneContainerManager` builds each pane's container from `netcruxPaneOverridesFactory` (`lib/services/workspace/netcrux_pane_overrides.dart`), which re-binds only `paneRenderStatsProvider`.

### 6.5 Action discovery: the descriptor table (single source of truth)

Every user-facing action is a `NetcruxAction` enum value; **`descriptorFor(NetcruxAction)` in `lib/core/shortcuts/netcrux_action_descriptors.dart` is the single source of truth for *where each action appears and when it is visible / enabled***. Each `NetcruxActionDescriptor` declares:

- `surfaces` — which of the three discovery surfaces list the action (`toolbar`, `menu`, `palette`). An empty set means keyboard/context-menu-only, and no action declares one today: `test/static/action_reachability_guard_test.dart` fails on any surfaceless action that is not on its (currently empty) allowlist, with its reason. The two X-trace openers were that list's only entries, held for exactly as long as their result panel did not exist.
- `isVisible(ctx)` — structural gating that removes the action from every surface.
- `isEnabled(ctx)` — transient gating over a `NetcruxActionContext` snapshot (open tab, laid-out design, selection, trace overlay, analysis results, comparison, waveform, pane count).

Presentation policy: the **menu bar** renders disabled items greyed out (`onSelected: null`); the **command palette** omits disabled actions (it has no greyed state); the **toolbar** renders disabled buttons; the **keyboard** dispatch path (`ShortcutManagerWidget.actionContextResolver`, wired by `WorkspaceScreen`) refuses to dispatch a disabled action's chord. All four consume the same derived selectors — `groupedActionsFor` / `paletteActionsFor` / `isActionEnabled` — over the shared `netcruxActionContextProvider` snapshot (`lib/features/workspace/providers/netcrux_action_context_provider.dart`), which combines workspace facts with the `activeTabActionFlagsProvider` root mirror of the active tab's per-tab state (per-tab providers are unreachable from the root scope; the mirror subscribes through the active tab's container via `tabContainerManagerHolderProvider`, which `bootstrap()` publishes).

Guardrails: (1) `descriptorFor` is an exhaustive `switch` — a new `NetcruxAction` fails to compile until a descriptor case is added; (2) `test/core/shortcuts/action_surface_conformance_test.dart` fails if any surface diverges from the table across a matrix of contexts; (3) gating inputs are added as fields on `NetcruxActionContext` (fed by the mirror), never read ad-hoc inside a surface. Per-surface hidden-action sets are banned — that architecture drifted per surface and was deleted.

The action's minimum license tier stays declared once on `NetcruxActionRequiredTier.requiredTier` (not duplicated on the descriptor); tier gating is orthogonal to enablement: tier-gated actions stay enabled + badged, and a post-beta insufficient-tier *activation* shows `NetcruxUpgradeDialog` (`lib/shared/widgets/netcrux_upgrade_dialog.dart`) from the deny path of `allowProAction` (`lib/features/workspace/services/pro_action_gate.dart`) instead of silently no-oping. An admitted Pro-tier action in a build without the Pro overlay (`proOverlayInstalledProvider`, `lib/core/providers/pro_overlay_installed_provider.dart`, overridden to true by the overlay) is refused with a "requires NetCrux Pro" snackbar, so the open-core no-op behind a badged action is never reached.

## 8. Coding Standards & Conventions

See `CLAUDE.md` for the binding day-to-day rules. The detailed rationale and the cross-platform mobile UI rules live in WaveCrux's `ARCHITECTURE.md` §8. netcrux inherits the Dart style, Riverpod, and testing conventions verbatim.

Comment prose is held to the clinical standard in the CLAUDE.md "Comment Hygiene" rule and enforced by `test/static/comment_hygiene_test.dart` (identical copy in the Pro overlay): no backlog/track identifiers used as anchors, no dates written as process notes, no session or reviewer voice. The guard reads comment text only — string literals are skipped, so identifier-shaped domain data (source-location fragments, FSM state names, fixture strings) cannot trigger it — and its allowlist is empty by construction.

The reference documents themselves are held to a matching standard by `test/static/doc_truth_test.dart`: every repo-relative path they name must exist (and every path they state is absent must stay absent), every quantity they state that is computable from the tree must equal the computed value, and every marked inventory block must equal the registry it claims to enumerate. Quantities that churn on every feature commit — an ARB key total, for instance — are written without a figure rather than guarded, since a number that forces a document edit on every string addition buys nothing.

### 8.9 Test Fixture & Validation Strategy

The netlist fixture corpus under `test/fixtures/netlist/` is the unit-test backbone, split `<design>/{generated,captured}/` and enforced by static guards in `test/static/`: `netlist_fixture_layout_test.dart` (no loose fixture at a design root), `netlist_fixture_companion_test.dart` (every `*.netlist.json[.gz]` has an `*.expected_netlist.json` golden; every malformed input has an `*.expected_error.json` companion), and `captured_fixture_licenses_test.dart` (captured designs carry a license from the allow-list). Scale designs (`chain_1k`, `chain_10k`, `grid_100k`, `mesh_1m`) plus real cores (`picorv32`, `vexriscv`) exercise the streaming reader and the elaboration/parse path documented above; `parseNetlistOnIsolate` is drop-in compatible with the in-memory `YosysJsonParser`, which now lives in the shared `crux_netlist` package (re-exported by `lib/services/yosys/yosys_json_parser.dart`) and is retained for tests. Pre-release manual verification is documented in `verification/` (see the CLAUDE.md "Verification Documentation Required" rule). This mirrors WaveCrux's layered strategy: cross-parser checks, hand-crafted known-answer fixtures, and golden snapshots.

## 9. Design System

Design tokens ship in `lib/core/theme/` — `netcrux_theme.dart` (`NetcruxTheme.light()` / `dark()` plus high-contrast variants selected when the OS asks for increased contrast, all derived from one brand seed), `netcrux_colors.dart`, `netcrux_theme_tokens.dart` (the chrome-token catalog registered with `crux_theme`), and `collaborator_palette.dart`. They follow WaveCrux's system (Material 3, dark default, 4dp/8dp grids, minimal motion); monospace fields use the platform `monospace` family. Brightness follows the active color preset rather than a separate light/dark switch: `netcrux_color_theme_bootstrap.dart` bridges the persisted preset and overrides into `crux_theme`, and `NetcruxApp` applies the preset's chrome tokens on top of the base theme.

## 10. Extension Points (Pro Overlay Seams)

netcrux is consumed by the closed-source Pro overlay through Riverpod provider overrides, not through code forking. The pattern matches WaveCrux exactly:

- `netcrux` (this repo) ships the complete standalone tool.
- The Pro overlay consumes this repo as a Git submodule, `path: ./netcrux` in pubspec, and layers `proOverrides` into the `bootstrap()` `UncontrolledProviderScope`.

When a Pro feature needs to plug into the open-core somewhere there is no hook yet, the *first* change is to this repo: define the interface, add the registry / Riverpod provider, ship a default no-op or open-core implementation. Only then does the Pro implementation land in the overlay (after a submodule pin bump). Forking open-core code in the Pro overlay is not allowed — see `CLAUDE.md` for the binding rule and `wavecrux/docs/ARCHITECTURE.md` §10 for the worked examples.

### Override pattern

```dart
// lib/app.dart
Future<void> bootstrap({
  List<String> args = const [],
  List<Override> extraOverrides = const [],
  List<Override> extraTabOverrides = const [],
  LinuxDesktopApp linuxDesktopApp = netcruxLinuxDesktopApp,
}) async {
  WidgetsFlutterBinding.ensureInitialized();
  final rootContainer = ProviderContainer(
    overrides: <Override>[
      // ...open-core root overrides first...
      ...extraOverrides, // the Pro overlay spreads its proOverrides here
    ],
  );
  final tabContainerManager = TabContainerManager(
    rootContainer: rootContainer,
    overridesFactory: (tabId) => <Override>[
      ...netcruxTabOverridesFactory(tabId),
      ...extraTabOverrides, // the Pro overlay spreads its proTabOverrides here
    ],
  );
  // bootstrap constructs the root ProviderContainer itself (rather than
  // letting ProviderScope build one implicitly) so TabContainerManager /
  // PaneContainerManager can parent per-tab / per-pane child containers
  // under it; UncontrolledProviderScope then adopts that container and
  // never disposes it — bootstrap owns it for the app's lifetime.
  runApp(
    UncontrolledProviderScope(
      container: rootContainer,
      child: WorkspaceManagersScope(
        tabContainerManager: tabContainerManager,
        paneContainerManager: PaneContainerManager(
          rootContainer: rootContainer,
          overridesFactory: netcruxPaneOverridesFactory,
        ),
        child: const NetcruxApp(),
      ),
    ),
  );
}
```

The Pro overlay calls `bootstrap(args: args, extraOverrides: proOverrides, extraTabOverrides: proTabOverrides, linuxDesktopApp: netcruxProLinuxDesktopApp)` from its `lib/main.dart`. `linuxDesktopApp` is the identity written into the AppImage desktop entry; it has to match the running binary's `APPLICATION_ID` (open core's default is `netcruxLinuxDesktopApp` in `lib/core/platform/netcrux_linux_desktop_app.dart`, checked against `linux/CMakeLists.txt` by `test/static/linux_desktop_identity_test.dart`). Open-core conflict semantics: open-core overrides come first (root via `netcruxTabOverridesFactory` / this list, per-tab via `extraTabOverrides`); Pro overrides come last; later overrides win. See `lib/app.dart` for the full implementation and `lib/services/workspace/netcrux_tab_overrides.dart` for the per-tab factory.

### CXP cross-probe extension points

NetCrux's CXP peer cross-probe server is open-core: cross-probe is suite-defining and free in every build, including the Cross-Probe panel's per-peer send, which originates a `request_highlight`. Only the Pro schematic context-menu originator is tier-gated. The seams are:

- `cxpServerHostProvider` (root scope) — `AsyncNotifierProvider` that owns the running `NetcruxCxpServer` lifecycle. Watches `appSettingsProvider` for the `cxpServerEnabled` / `cxpServerPort` flags; starts the server on launch when enabled. Disposing the provider tears the server down and removes the discovery manifest.
- `cxpPeersProvider` (root scope) — `StreamProvider<List<CxpPeerEntry>>` populated by the discovery watcher. The cross-probe panel `ref.watch`es this.
- `cxpEventLogProvider` (root scope) — `NotifierProvider<CxpEventLogNotifier, List<CxpEventLogEntry>>` holding a newest-first rolling buffer (`kCxpEventLogCapacity`, 50 entries) of inbound messages, presence changes and panel sends (`recordOutbound`), with `clear` behind the panel's Clear events action. The automatic `notify_selection` broadcasts are not recorded.
- `cxpManifestDirectoryProvider` — resolves the shared `crux/cxp/peers` directory through `crux_cxp`'s `sharedCxpManifestDirectory()` (environment-derived, deliberately not `path_provider`); overridable in tests.
- `netcruxProductVersionProvider` — version reported in the peer manifest and handshake: the running build's version from `aboutBuildInfoProvider`, or `dev` when the platform cannot report one.
- `NetcruxNameResolver` (`lib/services/remote/cxp/netcrux_name_resolver.dart`) — translates NetCrux's Yosys-elaborated names into and out of canonical `ElementId` form. Mapping documented as code comments alongside each kind branch. Outbound selections are resolved by `lib/services/remote/cxp/cxp_selection_resolver.dart`, which emits clean dot-joined names (`top.u_cpu`, `top.scope.netName`) and sends a register cell as the `net` named after its output.
- `EditorOpenService` (`lib/services/remote/cxp/editor_open_service.dart`) — launches the configured editor, without a shell, for an inbound `request_open_source` or a `request_highlight` of kind `source`. It is CXP-only: a local "show me the source" gesture goes to the RTL source pane instead. Process-runner overridable for tests.

The CXP server's inbound and selection-broadcast wiring lives in `lib/services/remote/cxp/cxp_inbound_handler.dart` (handles `request_highlight`, `notify_selection`, `request_open_source` and `request_open_artifact` against the active tab, with a shared-workspace fallback keyed by `crux.design_id`) and `lib/services/remote/cxp/cxp_outbound_emitter_controller.dart` (broadcasts `notify_selection` on every selection change while the `broadcastSelectionOnCrossProbe` setting is on). Both are mounted into the workspace shell as invisible widgets — `CxpInboundListener` wrapping the workspace body, and `CxpOutboundEmitter` via the per-tab `ActiveTabCxpEmitter` — so their per-tab `ProviderContainer` lookups resolve to the focused tab.

The Pro overlay overrides none of these providers. Its originate-side feature registers a per-tab `CrossProbeOriginator` and a schematic context-menu builder (see the context-menu seam below) that send a single-element `request_highlight` through `NetcruxCxpServer.requestHighlight` / `sendTo` on the same protocol bindings.

### Tracing seams

- `ConeOfInfluenceService` (`lib/domain/interfaces/cone_of_influence_service.dart`) + `coneOfInfluenceServiceProvider` (`lib/services/schematic/cone_of_influence_service_provider.dart`) — the Pro multi-step fanin / fanout cone-of-influence interface. Open-core registers a `NoopConeOfInfluenceService` default; the Pro overlay's `proOverrides` registers a concrete BFS implementation. Dispatch lives in `WorkspaceActionDispatcher` (`lib/features/workspace/services/workspace_action_dispatcher.dart`) against `NetcruxAction.showConeOfInfluenceFanin` / `showConeOfInfluenceFanout`, with the resulting `TraceOverlay` written into the active tab's `traceOverlayProvider`.
- `XTraceService` (`lib/domain/interfaces/x_trace_service.dart`) + `xTraceServiceProvider` (`lib/services/schematic/x_trace_service_provider.dart`) — the Pro X-trace causal-chain interface that walks backward through the driving cone of a selected net. Layout-agnostic and tier-agnostic: renders the empty-state explainer when no analysis result is set, or the crossings grouped by source→destination reset-domain pair (severity icon + signal name + localized `kind · synchronizer status · polarity · confidence` subtitle per row), honoring the state provider's severity filter. The hosting Pro panel mounts it as its body and adds chrome around it (tier badge + summary header, severity filter chips mutating the same provider, re-run action, footer). That panel is the only mount; an open-core build refuses the reset-domain actions with "requires NetCrux Pro". There is no domain-graph alternate visualization.
- `showResetDomainAnalysisPaneOpenerProvider` / `runResetDomainAnalysisOpenerProvider` / `showResetCrossingForSelectedSignalOpenerProvider` / `clearResetAnalysisSelectionOpenerProvider` (`lib/services/reset_domain/reset_domain_pane_openers.dart`) — open-core opener seams keeping the four `NetcruxAction.showResetDomainAnalysisPane` / `runResetDomainAnalysis` / `showResetCrossingForSelectedSignal` / `clearResetAnalysisSelection` actions discoverable in the command palette / menu bar on open-core builds. Defaults are no-ops; the Pro overlay overrides each provider in `proOverrides` with a callback that mounts the actual panel, runs full-design analysis, scopes the panel to a specific signal's crossings (resolving the active-selection fallback when no signal id is supplied), or clears the per-tab selection. ### Switching Activity Heatmap seam

- `WaveformSourceService` (`lib/domain/interfaces/waveform_source_service.dart`) + `waveformSourceServiceProvider` (`lib/services/waveform/waveform_source_service_provider.dart`) — the open-core seam through which the Pro overlay loads VCD/FST/GHW waveform files for the Switching Activity Heatmap (and any future NetCrux waveform-consuming feature — X-trace v2's value-sampling, simulator-correlated cross-probe). Seven members: `loadWaveform(filePath)` returns a [`WaveformSource`](../lib/domain/models/activity/waveform_source.dart) (path, detected format, load timestamp, cheap stable fingerprint, file size); `unloadWaveform()` closes the active source; `queryNetTransitions(netPath, {startNs, endNs})` returns the value transitions for a hierarchical net path inside a half-open window; `loadedNetPaths` enumerates the hierarchy; `sourceEndNs` and `currentSource` expose source metadata; `events` emits lifecycle [`WaveformSourceEvent`](../lib/domain/models/activity/waveform_source_event.dart)s. Open-core registers `NoopWaveformSourceService`: `loadWaveform` throws `UnimplementedWaveformLoad`, so a test can drive the load path without the Pro overlay; every other operation returns empty / null / 0. An open-core build never reaches it: the waveform actions are Pro-tier and are refused with "requires NetCrux Pro". The Pro overlay registers a concrete `ProWaveformSourceService` (a pure-Dart VCD parser; FST and GHW are not read) in **both** `proOverrides` (root, so the Open/Close Waveform actions resolve before a tab is focused) and `proTabOverrides` (per tab). The implementation is stateful — parsed VCD, current source, lifecycle event stream — so a root-only registration made every tab share one loaded waveform. Its derived view `currentWaveformSourceProvider` re-binds per tab alongside it; both registrations close the service on container disposal.
- `WaveformSource` / `WaveformFormat` / `WaveformTimeRange` / `NetActivity` / `ActivityAnalysisResult` / `ActivityAnalysisOptions` / `ActivityColorScheme` / `ActivityNormalization` / `WaveformSourceEvent` (`lib/domain/models/activity/`) — pure-data value types crossing both seams. `WaveformTimeRange.fullSimulationSentinel` is the analyzer's "expand against the source's end time" marker; `ActivityNormalization` covers `perNet` (linear against the max observed transition count) / `globalMax` (an alias with the same math, kept as a separate dropdown label) / `logScale` (log against max — preserves low-end separation); `ActivityColorScheme` covers `heatmapRedBlue` (blue→yellow→red), `heatmapViridis` (matplotlib viridis-inspired perceptually-uniform), and `heatmapGrayscale` (accessibility-first, prints/photocopies cleanly). `ActivityColorScheme.colorForScore(double)` is deterministic — same score + same scheme always yields the same color — so widget tests can assert RGB values without goldens.
- `ActivityAnalysisService` (`lib/domain/interfaces/activity_analysis_service.dart`) + `activityAnalysisServiceProvider` (`lib/services/activity/activity_analysis_service_provider.dart`) — the open-core seam for the per-net switching-activity computation. Three operations: `analyze({options})` walks the loaded netlist + waveform source and returns an [`ActivityAnalysisResult`](../lib/domain/models/activity/activity_analysis_result.dart) (per-net activity map, hottest / coldest top-N convenience lists, total transitions, analysis duration); `activityForNet(netPath, range)` is the focused single-net query; `analysisInvalidated` emits when the waveform source unloads/reloads or the netlist re-elaborates so the per-tab cache can refresh. Open-core registers `NoopActivityAnalysisService`: `analyze` returns the empty result, `activityForNet` returns null, `analysisInvalidated` never emits. The Pro overlay registers a `ProActivityAnalysisService` (in `proOverrides` and `proTabOverrides`) that composes the per-net transition computation with a small LRU cache keyed by source fingerprint, scope, time range, normalization, top-N and excluded net paths.
- `netActivityColorOverrideProvider` (`lib/services/schematic/net_activity_color_override_provider.dart`) — the schematic painter extension point. Exposes an optional `Map<String, Color>?` keyed by [`SchematicEdge.id`](../lib/domain/models/schematic/schematic_graph.dart). When an edge id appears in the map the painter renders the wire at that color in place of the default base paint (selection + dim overlays still win — activity coloring sits between the dim pass and the selection pass). Open-core defaults to `null` so wires render at the theme's `onSurfaceVariant`; the Pro overlay overrides the provider with its color-override controller. Threaded through `SchematicCanvas.netActivityColorOverride` into `SchematicCanvasRenderObject._paintEdges` — the same pattern as the existing `cellBodyPainterFactory` extension point.
- `ActivityHeatmapNotifier` + `activityHeatmapStateProvider` (`lib/features/activity/providers/activity_heatmap_state_provider.dart`) — per-tab state notifier holding the most-recent [`ActivityAnalysisResult`], the focused net path (drives schematic selection-sync), the active [`WaveformTimeRange`], and the active [`ActivityColorScheme`]. `setResult` reconciles selection when the focused net path is no longer present. `perTabActivityAnalysisResultProvider`, `selectedNetActivityProvider`, `activeActivityTimeRangeProvider`, and `activeActivityColorSchemeProvider` are convenience read-sides so widgets rebuild only on the slice they care about. The notifier and its read-sides are re-bound per tab by the Pro overlay's `proTabOverrides`, not by `netcruxTabOverridesFactory`.
- `ActivityHeatmapPane` widget (`lib/features/activity/widgets/activity_heatmap_pane.dart`) — the open-core renderer. Layout-agnostic and tier-agnostic: renders the empty-state explainer when no analysis result is set, or a fallback list view (hottest top-N above + coldest top-N below, each row carrying a per-net activity-score visual bar) when one is. The hosting Pro panel wraps it in the actual time-range / color-scheme picker + dockable chrome, and is the only mount; an open-core build refuses the activity actions with "requires NetCrux Pro".
- `showActivityHeatmapOpenerProvider` / `openWaveformFileOpenerProvider` / `closeWaveformFileOpenerProvider` / `runActivityAnalysisOpenerProvider` / `clearActivityColoringOpenerProvider` / `configureActivitySchemeOpenerProvider` (`lib/services/activity/activity_heatmap_pane_openers.dart`) — open-core opener seams keeping the six `NetcruxAction.showActivityHeatmap` / `openWaveformFile` / `closeWaveformFile` / `runActivityAnalysis` / `clearActivityColoring` / `configureActivityScheme` actions discoverable in the command palette / menu bar on open-core builds. Defaults are no-ops; the Pro overlay overrides each provider in `proOverrides` with its implementation of the action. Clearing is never tier-gated.

### Beta-release infrastructure seams

NetCrux consumes three cross-suite packages from `crux-shared/packages/` for the beta-release infrastructure: `crux_updates` (update check + banner), `crux_issue_reporter` (beta issue reporter), and `crux_license`'s beta-expiry half. The packages own the behaviour; NetCrux owns the configuration, the ARB-backed string adapters, the persisted settings, and the privacy-scrubbed session snapshot. The bindings are spread into the root container by `bootstrap` via `netcruxAppOverrides` (`lib/app.dart`) — [`netcruxUpdateOverrides`](../lib/features/update/netcrux_update_overrides.dart), [`netcruxIssueReporterOverrides`](../lib/features/issue_reporter/netcrux_issue_reporter_overrides.dart), [`netcruxTelemetryOverrides`](../lib/features/telemetry/netcrux_telemetry_overrides.dart) and the `crux_audit` product id — so the Pro overlay's `proOverrides` can layer on top under the usual later-wins semantics. The localized string bundles are the exception: `CruxUpdateStrings`, `CruxIssueReporterStrings` and `CruxTelemetryStrings` need `L10N.of(context)`, so `NetcruxApp` overrides `cruxUpdateStringsProvider`, `cruxIssueReporterStringsProvider` and `cruxTelemetryStringsProvider` from a nested `ProviderScope` inside `MaterialApp.builder`, alongside the screenshot `RepaintBoundary`, the desktop menu bar, the beta-expiry gate, the telemetry consent gate, and the update banner.

- `netcruxTelemetryOverrides` (from `crux_telemetry`) — binds the product config, consent and installation-id storage, URL launcher, app version, form factor and locale. The pipeline is inert during the beta: nothing is recorded or sent and neither consent surface (the first-launch disclosure, `Settings → Privacy`) mounts, unless the build sets `--dart-define=TELEMETRY_DEV=true`. Once the beta flag is off, the user's answer decides, and an Enterprise policy file overrides it.

- `cruxIssueReporterDataProviderProvider` (from `crux_issue_reporter`) — the **overlay seam** for the issue reporter. Open-core registers `NoopCruxIssueReporterDataProvider`, which contributes no extra categories; the Pro overlay registers a data provider that appends a "Pro State" category. It reads the structured `attributes` map that [`buildNetcruxIssueSessionContext`](../lib/features/issue_reporter/providers/netcrux_issue_session_context.dart) publishes (`openTabCount`, `hasNetlist`, `moduleCount`, `cellCount`, `activeProSurfaces`) rather than re-resolving the active tab's container itself, and localizes its category title from `CruxIssueSessionContext.localeTag` — the interface is pure Dart and carries no `BuildContext`.
- `cruxIssueSessionContextProvider` (from `crux_issue_reporter`) — the **product seam**, bound by open-core to `buildNetcruxIssueSessionContext`. It resolves the active tab's per-tab `ProviderContainer` through [`TabContainerManagerHolder`](../lib/services/workspace/tab_container_manager_holder.dart), the same root-mirror route `ActiveTabActionFlagsNotifier` uses; reading those providers off `ref` would silently return the root container's empty project. Its output is bound by the reporter's privacy contract: counts, fixed enumeration values and language names only — never a filesystem path, never an identifier taken from the user's RTL. That is also why Yosys stderr is deliberately not wired into `cruxIssueDiagnosticsReportProvider`: it quotes source-file paths verbatim.
- `observedServerTimeSinkProvider` (from `crux_updates`) → [`ObservedServerTimeStore`](../lib/features/update/providers/observed_server_time_provider.dart) → `observedServerTimeProvider` (from `crux_license`) — the clock-hardening loop. `crux_updates` reports the manifest's `server_time` on every successful fetch but deliberately does not persist it; NetCrux's store advances monotonically, persists to `SharedPreferences`, and reloads on launch, and its value is fed back into `crux_license` so `trustedBetaExpiryNow` reckons beta expiry against the later of the device clock and that watermark. Winding the device clock back therefore cannot defer expiry.

### Extra localizations delegates seam

- `extraLocalizationsDelegatesProvider` (`lib/plugins/extra_localizations_delegates_provider.dart`) — the open-core seam through which the Pro overlay contributes additional `LocalizationsDelegate`s without forking `NetcruxApp` or `bootstrap`. Default returns an empty list; `NetcruxApp.build` concatenates it after open-core's `L10N.delegate` + the global Material/Widgets/Cupertino delegates and hands the combined list to `MaterialApp.router`. The Pro overlay's `proOverrides` overrides this provider with `[L10NPro.delegate]` so any Pro widget that calls `L10NPro.of(context)` resolves to a real `L10NPro` instance. This keeps Pro-only strings (e.g. cross-probe context-menu / snackbar messages) inside the overlay's own ARB files rather than violating the open-core / Pro boundary by living in `netcrux/lib/l10n/`. Mirrors `wavecrux/lib/plugins/extra_localizations_delegates_provider.dart`.

| **ActivityAnalysisResult** | Pure-data result bundle (`lib/domain/models/activity/activity_analysis_result.dart`): `source` (or null) + `timeRange` + unmodifiable `perNetActivity` map + `totalTransitions` + sorted `hottest` / `coldest` top-N convenience lists + `analysisDuration`. `ActivityAnalysisResult.from(...)` is the canonical constructor that computes top-N + totals from a raw per-net map. JSON round-trippable. |
| **ActivityAnalysisOptions** | Pure-data tuning bundle (`lib/domain/models/activity/activity_analysis_options.dart`) for `ActivityAnalysisService.analyze`: optional `scopeFilter` (`ElementId`), `timeRange` (defaults to the full-simulation sentinel), `normalization`, `topN`, and an `excludedNetPaths` blocklist. |
| **ActivityNormalization** | Enum (`lib/domain/models/activity/activity_normalization.dart`) controlling how raw transition counts map to normalized scores: `perNet` (linear against max observed — the hottest net pins to 1.0; a single outlier like a clock crushes the rest near 0) / `globalMax` (an alias of `perNet` with identical math, kept as its own dropdown label) / `logScale` (log against max — preserves low-end separation). |
| **ActivityColorScheme** | Enum (`lib/domain/models/activity/activity_color_scheme.dart`) with the three built-in heatmap palettes: `heatmapRedBlue` (blue at 0.0 → yellow at 0.5 → red at 1.0; the classic thermal-imaging metaphor), `heatmapViridis` (matplotlib viridis-inspired, perceptually uniform), `heatmapGrayscale` (accessibility-first, prints / photocopies cleanly). `colorForScore(double)` is deterministic — same score + same scheme always yields the same color — so tests can assert RGB values without goldens. |
| **WaveformSourceEvent** | Sealed-class lifecycle event (`lib/domain/models/activity/waveform_source_event.dart`) emitted by `WaveformSourceService.events`. Three variants: `WaveformSourceLoadedEvent(source)`, `WaveformSourceUnloadedEvent(previousFilePath)`, `WaveformSourceLoadFailedEvent(filePath, message)`. The `currentWaveformSourceProvider` `StreamProvider` watches this and re-emits the active source on every load / unload. |
| **WaveformLoadException** / **UnimplementedWaveformLoad** | Exception (`lib/domain/interfaces/waveform_source_service.dart`) raised by `WaveformSourceService.loadWaveform` on any load failure (missing file, unsupported format, parse error, hierarchy mismatch). `UnimplementedWaveformLoad` is the open-core sentinel subclass raised by `NoopWaveformSourceService` so the action dispatch path is exercised in tests without the Pro overlay present. |
| **netActivityColorOverrideProvider** | Open-core `Provider<Map<String, Color>?>` (`lib/services/schematic/net_activity_color_override_provider.dart`) — the schematic painter extension point through which the Pro overlay's Switching Activity Heatmap publishes a per-edge color override map keyed by [`SchematicEdge.id`](../lib/domain/models/schematic/schematic_graph.dart). When an edge id appears in the map the painter renders the wire at that color in place of the default base paint (selection + dim overlays still win). Open-core default is `null`; the Pro overlay overrides it with a per-tab notifier that derives the map from the tab's activity result, color scheme and the scope on the canvas, resolving each laid-out edge to a waveform net path. |
| **ActivityHeatmapNotifier** | Per-tab `Notifier<ActivityHeatmapState>` (`lib/features/activity/providers/activity_heatmap_state_provider.dart`) holding the most-recent `ActivityAnalysisResult`, the focused net path (drives schematic selection-sync), the active `WaveformTimeRange`, and the active `ActivityColorScheme`. `setResult` reconciles the focused net path against the new result; `selectNet` accepts only valid paths; `setTimeRange` / `setColorScheme` update independently; `clearSelection` / `reset` wipe partial / full state. Re-bound per tab by the Pro overlay's `proTabOverrides`. |
| **ActivityHeatmapPane** | Open-core renderer widget (`lib/features/activity/widgets/activity_heatmap_pane.dart`) that reads the per-tab `activityHeatmapStateProvider`. Renders the empty-state explainer when no analysis has run or a fallback list view (hottest top-N above + coldest top-N below, each row carrying a per-net activity-score visual bar) when one has. Layout-agnostic; the Pro overlay wraps it in the actual time-range / color-scheme picker + dockable chrome. |
| **showActivityHeatmapOpenerProvider** / **openWaveformFileOpenerProvider** / **closeWaveformFileOpenerProvider** / **runActivityAnalysisOpenerProvider** / **clearActivityColoringOpenerProvider** / **configureActivitySchemeOpenerProvider** | Open-core `Provider`s (`lib/services/activity/activity_heatmap_pane_openers.dart`) for the Switching Activity Heatmap's UI entry-points. All six default to no-op so `NetcruxAction.{showActivityHeatmap,openWaveformFile,closeWaveformFile,runActivityAnalysis,clearActivityColoring,configureActivityScheme}` stay palette-discoverable on Open Core; the Pro overlay overrides each with its implementation of the action. |
